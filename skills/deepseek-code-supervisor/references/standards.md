# 操作规范与判断意见

二轮检测管"查"，这份管"写"。查得再细，写的时候没想清也是白查。

不是风格指南。每条都是踩过坑之后的结论，违反会直接导致返工或线上事故。
返工单里要**点名违反的是哪一条**，光说"代码质量不高"没用。

---

## 一、动手顺序

1. **先跑通再改。** 改之前让项目跑起来，知道基线长什么样。跑不起来的，先修到能跑 —— 否则改完分不清是新错还是旧错。
2. **先复现再修。** bug 复现不了就不改。改完不知道好没好，等于没修。
3. **先定验收再动手。** 写不出验收，说明需求没听懂，回去问。
4. **先读后写。** 改一个函数前，先看谁在调它。`grep` 一遍调用点，比读十遍实现有用。
5. **一次只改一件事。** 同时改三处，出问题无法二分定位。
6. **改前留回滚点。** 提交、备份、记 md5，三选一。没有回滚点的改动不许开始。

## 二、文件与命名

1. **文件名说清用途。** `utils.js`、`helpers.py`、`common.ts` 是垃圾桶，谁都能往里扔。出现第二个用途就拆出去。
2. **命名用业务词，不用技术词。** `invoiceTotal` 好过 `data2`，`retryPayment` 好过 `handleClick`。
3. **布尔值以 `is/has/can/should` 开头。** `isExpired`、`hasPermission`。别用 `flag`、`status`。
4. **函数名是动词，变量名是名词。** `getUser()` 返回对象；`user` 是对象本身。
5. **单位写进名字。** `timeoutMs`、`sizeBytes`、`priceCents`。不写单位的数字，三个月后没人知道是秒还是毫秒。
6. **常量集中一处。** 散落的魔法数字是 bug 的温床。
7. **一个文件超过 400 行考虑拆。** 不是硬规则，但超过就是信号。

## 三、函数与结构

1. **一个函数做一件事。** 名字里出现"并且"就该拆。
2. **超过 50 行考虑拆，超过 80 行必须拆。**
3. **参数超过 4 个改成对象。** 调用方不用记顺序，加参数不用改所有调用点。
4. **嵌套超过 3 层用早返回。** `if (!valid) return;` 一路往下，比金字塔好读。
5. **副作用写在名字里。** `saveUser()` 会写库，`formatUser()` 不该写。
6. **不修改传进来的参数。** 复制一份再改，调用方不该被偷袭。
7. **宁可重复三行，不要提前抽象。** 抽象的代价是耦合，重复的代价是改三处。前者更贵。

## 四、错误处理

先分类，再决定怎么处理。三类混在一起处理，必然有一类被吞掉。

| 类型 | 例子 | 正确做法 |
|---|---|---|
| **用户输入错误** | 手机号格式不对、必填项缺失 | 返回可读提示，不改系统状态，日志记 info 不记 error |
| **可恢复的外部失败** | 网络超时、限流、第三方 5xx | 重试（指数退避，最多 2 次）+ 降级 + warn 日志 |
| **不可恢复的程序错误** | 配置缺失、数据结构不符、除零 | fail fast，error 日志带上下文，不静默吞 |

**错误信息公式**：`做什么` 失败：`对什么`，原因 `X`。下一步：`Y`。

```
读取配置 config.json 失败（ENOENT）：文件不存在。请检查 CONFIG_PATH 环境变量。
```

不合格的写法：

```
Error: undefined
出错了
请求失败
```

**禁止**：

- `catch {}` / `except: pass`。最差也要 `log.warn(e)` 加一行说明。
- 用 `return null` 表示"出错了"和"本来就是空"两种意思。
- 把异常包装成成功返回（`{success: true, data: null}`）。
- 错误信息里带内部路径、SQL、堆栈给终端用户看。

## 五、日志

1. **四级够用**：error（要人介入）/ warn（降级但能跑）/ info（关键状态变更）/ debug（默认关）。
2. **关键路径记两头**：开始、结束、耗时。出问题才知道卡在哪。
3. **不打敏感信息**：密码、token、完整手机号/身份证、完整请求体。
4. **一条日志 ≤ 200 字**，超过说明你把对象整个打进去了。
5. **日志要能定位**：带上模块名、ID、关键参数。只有一句"失败了"的日志等于没打。

## 六、配置与环境

1. **配置集中一处**，不要散落 `os.environ[...]` / `process.env.X`。
2. **有 `.env.example`**，字段和代码里读的一一对应。少一个字段，换台机器就跑不起来。
3. **启动时校验必填项**，缺了就 fail fast。别跑到第三步才炸。
4. **默认值写代码里**，不写文档里。文档会过期，代码不会。
5. **环境显式区分**，别靠"有没有某个变量"猜是生产还是开发。
6. **密钥不进代码、不进仓库、不进构建产物。** 用环境变量或密钥管理。

## 七、接口设计

1. **错误响应统一结构**：`{code, message, detail?}`。前端只写一套错误处理。
2. **列表统一结构**：`{items, total}` 或游标分页。别这接口返数组、那接口返对象。
3. **分页默认 20，上限 100。** 不设上限的列表接口，迟早被一条 10 万行的请求打死。
4. **时间统一 ISO8601 UTC 存**，展示层本地化。别在数据库里存"2026-11-03 13:00"这种没有时区的字符串。
5. **ID 统一字符串**。数字 ID 在 JS 里超过 2^53 会精度丢失。
6. **写操作要幂等**：幂等键或唯一约束。用户双击提交是常态。
7. **破坏性改动加版本或加新字段**，别原地改语义。老客户端还在跑。

## 八、数据与迁移

1. **迁移必须可回滚**，且迁移前有备份。不可回滚的迁移等于单向门。
2. **大表 DDL 注意锁**。线上加字段、加索引都可能锁表，先查清楚。
3. **索引跟着查询走**，不凭感觉加。加了不用的索引是写入负担。
4. **SQL 参数化**，不拼字符串。这条没有例外。
5. **生产不跑没有 where 的 update / delete。** 先 `select count(*)` 看一眼影响行数。
6. **删除优先软删或先标记**，给自己留反悔的余地。

## 九、测试

1. **测行为，不测实现。** 测"输入 A 得到 B"，不测"内部调了哪个函数"。否则一重构全红。
2. **一个测试一个主题。** 一个测试里断言十件事，挂了不知道哪件。
3. **名字写场景**："空列表时返回 0 而不是崩溃"，不写 "test_getList_2"。
4. **至少三组**：正常 / 边界（空、单条、超长）/ 失败（非法输入、外部报错）。
5. **断言必须能失败。** 改坏一个字节还绿，就是哑弹（第 2 项）。
6. **不为覆盖率写测试。** 覆盖率是结果，不是目标。
7. **修 bug 先补一条会红的测试**，再修。修完它变绿，才算修好。

## 十、提交与交付

1. **一次提交一件事。** 混在一起，出问题无法二分。
2. **提交信息首行 ≤ 50 字，写"为什么"**，不写"改了什么"（diff 已经说了）。
3. **不提交**：注释掉的代码、调试输出、临时文件、`.env`、构建产物。
4. **提交前跑一遍验证命令。** 没跑过就不许提交。
5. **交付附三样**：改动清单、验证记录、未验项。缺一样按没交付处理。
6. **交付前 `git status` 看一眼。** 有没有误加的、误删的、忘记 add 的。

## 十一、性能

1. **先测量再优化。** 直觉指出的瓶颈，八成不是瓶颈。
2. **N+1 查询优先查。** 循环里查数据库是最常见的性能杀手。
3. **缓存最后加**，而且必须同时想好失效策略。加缓存不难，难的是数据不对时怎么发现。
4. **不做微优化。** 把 `for` 改成 `forEach` 省不了时间。
5. **列表接口必须分页**，见七·3。

## 十二、安全

1. **输入不信任**，在边界做校验。前端校验是体验，后端校验才是安全。
2. **权限检查在后端**。前端隐藏按钮不叫权限控制。
3. **密钥不进代码**，见六·6。
4. **SQL 参数化**，见八·4。
5. **文件路径防穿越**：拼路径前做规范化，拒绝 `../`。
6. **错误信息不泄露内部结构**：不给用户看堆栈、SQL、文件路径。
7. **依赖有已知漏洞就升**，别拖。尤其是直接暴露在公网的服务。

# 判断意见

这一节是观点，不是规范。不同意可以不照做，但要先想清楚为什么。

### 1. 能用标准库就别加依赖

加一个依赖 = 加一个维护对象 + 一个供应链风险 + 一个版本冲突源。
为了省 20 行代码引入一个库，通常不划算。

### 2. 三遍法则

同一段逻辑**第三次**出现再抽象。第二次就抽象，通常是把两个碰巧相似的东子强行合并，
第三次出现时你会发现方向错了。

### 3. 别为"以后可能要用"加参数

YAGNI 在个人项目里几乎总是对的。多一个开关，就多一条没人测过的分支。
真要用的时候加，成本比现在低。

### 4. 删代码优于注释代码

注释掉的代码不会被执行，也不会被维护，只会误导下一个人。
git 记着历史，放心删。

### 5. 重构前先补测试

没有测试的重构，你分不清"改好了"和"改坏了"。改完发现坏了，也说不清是哪一步坏的。

### 6. "好像有点问题"就先写个断言钉住

说不清哪里不对的时候，写一条断言把当前行为固定下来。跑一下：
红了，说明你发现问题了；绿了，说明你的怀疑是错的。两种结果都比"再看看"有用。

### 7. 一次只做一件事

同时改三个地方，出问题无法二分定位。这句在"动手顺序"里写过，再说一遍因为最容易违反。

### 8. 没有测量就不优化

你的直觉 80% 是错的，剩下 20% 里的大多数也不是瓶颈。
先加一个计时，再决定改哪里。

### 9. 日志比断点值钱

断点只能在本地用，线上问题只能靠日志。写代码时顺手加的那两行，是半夜排障时唯一的线索。

### 10. 需要写三页文档解释的方案，多半设计复杂了

好的设计一句话能说清。说不清的时候，先简化，别写文档。

### 11. AI 生成的代码，先看失败路径

看它有没有处理：空输入、网络失败、权限不足、并发写冲突。
没处理的，一律不信 —— 包括你自己刚写的那段。

### 12. 选型优先选"能换掉"的

两个方案差不多时，选更容易替换的那个。可逆性比性能、比优雅都值钱，
因为你对未来的判断大概率是错的。

### 13. 拿不准就问，但先给默认方案

让人做选择题，不做填空题。
"我按 A 处理，理由是 X，要改成 B 说一声" —— 这句话比"你要用 A 还是 B"效率高得多。
